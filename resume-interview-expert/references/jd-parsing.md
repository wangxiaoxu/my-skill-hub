# JD 拆解：把招聘广告还原成要求清单

JD 是营销文案和要求清单的混合体。拆解的目标不是「读懂」，而是产出可以逐条打勾、逐条准备证据的表。

## 1. 三层结构

| 层 | 内容 | 处理方式 |
|---|---|---|
| 硬性要求 | 学历、年限、专业、证书、必须掌握的技能 | 逐条判定「有 / 部分 / 无」，无则评估是否硬伤 |
| 加分项 | 「优先」「最好有」「了解」后面的内容 | 有则前置，无则不硬编 |
| 隐含信号 | 团队阶段、协作方式、工作强度、汇报关系 | 转成面试问题，判断匹配度 |

## 2. 硬性要求识别

高频标记词：

- 学历与年限：`本科及以上`、`3年以上`、`5年+`、`统招`
- 必须技能：`精通`、`熟练掌握`、`必须具备`、`must`、`required`
- 领域经验：`有 X 行业经验`、`熟悉 X 协议`
- 证书/资格：`CPA`、`PMP`、`法律职业资格`

处理规则：

1. 一条要求里出现多个技能时拆成多条，例如「精通 Java，熟悉 Spring Boot 与 MySQL」拆成 3 条。
2. `精通` 与 `熟悉` 不是同一档：前者要能讲原理与取舍，后者能上手即可。
3. 年限是粗筛条件，不等于能力；年限不足但有对等项目证据时，在简历里用项目规模补位。

## 3. 加分项识别

标记词：`加分`、`优先`、`最好有`、`了解`、`nice to have`、`plus`、`preferred`、`bonus`。

注意两种陷阱：

- **「了解」有时是硬要求**：出现在「任职要求」正文里、且是该岗位的核心工具时，按硬性处理。
- **「优先」可能是实际门槛**：如果团队里人人都有该技能，它就不是加分而是默认项。判断方法：看 JD 里该技能出现的次数与位置。

## 4. 隐含信号

| 原文信号 | 可能含义 | 面试要问 |
|---|---|---|
| 从 0 到 1 / 搭建 | 需要能独立定义问题 | 你做过最接近 0 到 1 的事是什么 |
| 跨团队推动 | 没有直接汇报权 | 你如何说服不向你汇报的人 |
| 快速迭代 / 敏捷 | 需求变化频繁 | 需求变更时你怎么排优先级 |
| 抗压 / 能接受挑战 | 加班或目标压力 | 最近一次高压交付是什么情况 |
| 数据驱动 | 需要能量化结果 | 你用什么指标判断成功 |
| 负责核心系统 | 稳定性要求高 | 你处理过最严重的一次线上故障 |

隐含信号不写进简历，但决定面试追问方向。

## 5. 关键词族

同一能力常有多种写法，归族后再对齐，避免漏匹配：

| 族 | 常见写法 |
|---|---|
| 容器编排 | Kubernetes、K8s、k8s、容器平台 |
| 消息队列 | Kafka、RocketMQ、RabbitMQ、MQ、消息中间件 |
| 数据库 | MySQL、PostgreSQL、PG、关系型数据库 |
| 前端框架 | React、React.js、Vue、Vue.js |
| 数据分析 | 数据分析、数据洞察、BI、指标体系 |
| 用户增长 | 用户增长、增长、拉新、获客 |
| 项目管理 | 项目管理、PMO、敏捷、Scrum |

## 6. 输出模板

```text
要求清单
| # | 原文 | 类型（硬性/加分/隐含） | 关键词族 | 我的证据 | 判定 |
|---|------|------------------------|----------|----------|------|
| 1 | 精通 Java | 硬性 | Java | 5 年后端，交易系统 | 有 |
| 2 | 熟悉 Kubernetes | 硬性 | 容器编排 | 主导容器化 | 有 |
| 3 | 有 Go 经验优先 | 加分 | Go | 内部调度服务 | 部分 |
```

判定只有三档：`有`（能给出项目与结果）、`部分`（用过但缺深度）、`无`（没有真实经历）。`部分` 和 `无` 都要写进缺口清单。

## 7. 常见错误

- 把公司介绍里的形容词当要求（「扁平化管理」「有激情」）。
- 把「岗位职责」当成「任职要求」：职责描述的是要做什么，不是你已经会什么。
- 只提取英文关键词，漏掉中文能力项（跨部门协作、用户增长）。
- 忽略地点、出差比例、排班等硬约束，面试后才发现不匹配。
- 把「优先」全部忽略，导致简历没有突出真正的差异化优势。
