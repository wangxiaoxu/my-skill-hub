# 日志取证：把碎片拼成时间线

日志排查失败，多数不是「没日志」，而是「时间对不上、来源对不上、看到的只是被采样后的样子」。本页只讲怎么把日志变成可信证据。

## 1. 时间线重建四步

1. **确定窗口**：先找「最后一次正常」与「第一次异常」，不要一上来就翻全量日志。
2. **归一化时间戳**：把不同格式统一成同一时区（建议 UTC）。混合格式直接排序必然错。
3. **标注来源**：每条事件保留 `文件名:行号`，否则无法回溯。
4. **找断点**：两个事件之间如果缺少预期的周期日志（心跳、access log、定时任务），断点本身就是证据。

命令行起步：

```bash
python3 scripts/log_timeline.py app.log access.log --since 2026-10-26T09:00:00 --json
```

无时间戳的行（多行堆栈、异常续行）会标成 `untimed` 并挂在同文件上一条时间戳上；它们只能当上下文，不能用来判断先后。

## 2. 跨源对齐

| 对齐键 | 适用场景 | 注意 |
|---|---|---|
| `trace_id` / `request_id` | 微服务、网关到后端 | 确认每一跳都透传，缺失处就是断链点 |
| 客户端 IP + 时间窗 | 网关、WAF、应用 | NAT 后 IP 会重复，不能当唯一键 |
| 用户 ID / 订单号 | 业务链路 | 注意脱敏后再写入文件 |
| 定时任务批次号 | 批处理、离线任务 | 批次号比时间更可靠 |

**时钟偏移**是跨源对齐的头号杀手。容器默认 UTC，宿主机可能是本地时区，应用日志又可能用 `Asia/Shanghai`。先用同一条已知事件的多个来源时间求差，算出偏移量再对齐。

## 3. 时区陷阱清单

- 容器内 `date` 与业务日志时间不一致：先看 `TZ` 环境变量与基础镜像默认时区。
- nginx `$time_local` 带 `+0800`，应用日志不带时区：后者按本地时间解释，排序会差 8 小时。
- MySQL `time_zone` 为 `SYSTEM` 时，`NOW()` 与 `UTC_TIMESTAMP()` 结果不同；应用写入的时间字段可能是 UTC。
- 前端上报时间戳常是毫秒 epoch，后端日志是秒 epoch，混在一起会差 1000 倍。
- 夏令时地区每年有 1 小时重复或缺失，跨时区业务建议全程 UTC。

## 4. 日志级别与采样偏差

看到的不等于发生的。排查前先确认：

1. **级别过滤**：生产常把日志级别设为 `WARN`，`INFO` 级别的关键上下文根本不存在。
2. **采样**：高 QPS 服务常对成功请求采样，对错误全量；用成功样本算比例会失真。
3. **异步缓冲**：进程被 `SIGKILL` 或 OOMKilled 时，缓冲区里最后几条日志会丢失；「日志突然中断」本身就是 OOM 或崩溃的信号。
4. **轮转与保留**：`logrotate` 切割后旧文件可能已被删除；先确认窗口内日志是否完整。
5. **重复采集**：sidecar 与应用同时输出到 stdout 时，同一条日志可能出现两次，计数翻倍。

判断采样是否影响结论：拿一个已知总量的指标（如网关请求数）与日志条数对比，比例明显小于 1 就说明有采样或丢失。

## 5. 脱敏清单（写入任何文件之前）

必须替换：

- `Authorization`、`Cookie`、`Set-Cookie`、`X-Api-Key` 等请求头值
- 手机号、邮箱、身份证号、银行卡号
- 内网 IP、主机名、数据库连接串中的账号密码
- 对象存储签名 URL 的 `Signature`、`X-Amz-Security-Token`
- 用户上传文件名中可能含个人信息的片段

替换方式：保留可排查的结构，例如 `user_id=u_<REDACTED>`、`token=<REDACTED>`，不要整行删除，否则丢失因果关系。

## 6. 快速检查表

- [ ] 时间窗口是否覆盖「最后一次正常」和「第一次异常」
- [ ] 所有来源是否已归一到同一时区
- [ ] 每条结论是否能指到具体文件与行号
- [ ] 是否确认日志级别足以覆盖该事件
- [ ] 是否排除了采样、轮转、缓冲丢失
- [ ] 引用片段是否已脱敏
- [ ] 是否把「日志没出现」误当成「事件没发生」
